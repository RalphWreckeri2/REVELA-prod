# Responsiveness benchmarks (manual, opt-in)

Nothing in this guide deploys or starts a scan, submits an inspection, resets a quota, or changes a database automatically. Use an **approved staging environment** for any full-detection or inspection trial. Never use a production account for write trials. Benchmark switches are **off by default**.

## Snapshot and workload

The read-only audit snapshot of the configured MySQL database found **602** official-registry records, **495** geospatial logs, **346** registry-only map rows, **841** unfiltered map rows, and **479** records with exact coordinates (470 logs + 9 registry-only). **Correction to the earlier audit:** `normalizeFlag()` substitutes a barangay centroid or default center for rows without exact coordinates, so the map attempts **841 markers**, not 479 (`revela_web/src/pages/MapPage.jsx:738–769, 1519–1635`). `geolocated_rows` and `expected_markers` are separate CSV columns. These are not permanent constants. Before every 10-trial series, verify the registry count from `GET /api/flags/detection-quota` (`registry_count`) and map counts from the first `GET /api/flags/?page=1&limit=1000` (`total`), then compare exact-coordinate and marker counts with the actual returned records. If they drift between trials, split the series. Do **not** assume 859 or equate registry rows with map rows.

* **Matching-only:** `POST /api/admin-settings/matching-dry-run`, exactly the **ten synthetic POIs** in `revela_web/public/data/responsiveness-matcher.json`, same order and coordinates every time, compared against the *current complete registry*. This endpoint reloads registry and uses the unindexed `_match_poi_to_registry` loop. It makes **zero Google requests**, writes no flags, and is **not** a scan or an indexed-matcher microbenchmark. Outcome `incomplete` if any candidate returns an error.
* **Full detection:** `POST /api/flags/run-detection`, one chosen mode (`quick` or `full`) per series. Includes synchronous reconciliation, grid selection, Google Nearby (or explicitly documented Test Mode fixture replay), matching and DB commits. The row's `map_rows`/`expected_markers` are the **pre-scan** map snapshot; scan results can change them. Record quota, completed/total grid points, `api_requests_consumed`, `fixture_requests_replayed`, matcher calls, checkpoint state, and `status` in CSV. A partial/coverage-gap/quota/cancellation outcome must remain in CSV but is **not** a full-completion sample. Comparable 10-run live scans may be impossible without an approved staging setup with consistent checkpoints, quotas, and POIs; do not reset production quota to force ten runs.
* **Map:** route `/map`, all sequential `GET /api/flags/` pages (1,000/page), normal Base Map and Flag Markers layers enabled. Ready means all pages received, coordinate-eligible markers created, clusterer finished, municipal `fitBounds` performed, final fitted tiles loaded, map idle and next animation frame. `data_ms`, `markers_ms`, `tiles_ms`, `ready_ms` are elapsed from navigation; `elapsed_ms` is readiness. A missing fit, failed fetch, or missing tile/cluster event produces a failure or a 60-second **incomplete** row, not a falsely fast success. `request_id` is the **last flags page**; use browser Network and `X-Request-ID` for per-page backend timings.
* **Online inspection:** Submit tap after validation, including GPS fix wait and any in-submit photo compression/upload; `accepted_ms` stops when Dio has received and validated the report-ID/status response from `POST /api/inspections/submit` (backend commit precedes this response), `visible_ms` stops after the snackbar is shown. `elapsed_ms=visible_ms`. Preuploaded evidence and zero/one/multiple in-submit files are **different series**. `savedOffline`, `needsAttention`, `already_accepted`, failed and incomplete are retained but **not** new successful submissions. If local caching fails *after* a confirmed commit, the row is `committed_local_failure`. `submissionReceivedAt` and an evidence-upload response do not establish a commit.

## Browser CSV (dry-run, full detection, map)

1. Sign into the **intended environment** in a desktop browser. In its console run:

   ```js
   revelaBenchmark.enable({cache: 'warm', network: 'wifi', fixture: 'responsiveness-matcher-v1', registry_rows: 602, map_rows: 841, geolocated_rows: 479, expected_markers: 841})
   ```

   Replace the counts with that session's verified counts and describe actual cache/network conditions. This toggle persists only for this browser tab's session. Do not include tokens, names, or personal data in settings. For cold browser trials, use a fresh browser context or disable cache/clear cache **before** each navigation; for warm trials keep the context and cache. Set `cache` accordingly using `revelaBenchmark.configure({...})`. Record whether navigation is SPA sidebar click or hard reload; don't pool the two. A hard `/map` reload uses Navigation Timing from document start; sidebar navigation starts at its click. For precise navigation-start timing, navigate using the sidebar from a different route or hard reload the map page, not a browser-back gesture.
2. For matching-only, in the browser console set `const candidates = await (await fetch('/data/responsiveness-matcher.json')).json()`, then **manually** invoke `await revelaBenchmark.dryRun(candidates)` ten times, sequentially. This is the only provided console call that sends a POST, and only the dry-run endpoint. Verify `results.length===10` each time. The helper reads the existing login token but never exports it.
3. For a full scan **only when approved on staging**, manually select one mode, click Run Detection, confirm, and wait for the response. Repeat at most ten authorized comparable runs. Do not treat SSE completion or the map-refresh dialog as the request's completion point. Capture `status`, work-budget fields and quota alongside the emitted CSV row; any absence is reported, not discarded.
4. For map, open `/map` ten times per cache/navigation variant, letting each trial complete or time out before leaving. Do not toggle off layers during a trial. Confirm the CSV `map_rows` matches the API `total` and `created_markers===expected_markers`. Record actual browser/Google Maps script/tile cache behavior using DevTools Network and the chosen cache label; do not label a warm run cold solely because the page reloaded.
5. `revelaBenchmark.rows()` previews rows, `revelaBenchmark.exportCSV()` downloads **one row per attempted trial**, including errors/incomplete outcomes. Export before closing the tab. `revelaBenchmark.clear()` starts a new series; `revelaBenchmark.disable()` disables further recording. Server logs `[req] id=... dur_ms=...` can be joined using the recorded `X-Request-ID`; server time is not client elapsed time. Do not subtract unsynchronized server/client wall-clock timestamps.

## Mobile CSV (online submission only)

Build a **staging-targeted** app with `--dart-define=REVELA_BENCHMARK=true` and `--dart-define=REVELA_BENCHMARK_NETWORK=wifi` plus `REVELA_BENCHMARK_CACHE=online`, `REVELA_BENCHMARK_REGISTRY_ROWS=602`, `REVELA_BENCHMARK_MAP_ROWS=841`, `REVELA_BENCHMARK_GEOLOCATED_ROWS=479`, `REVELA_BENCHMARK_MARKERS=841` (substitute the staging snapshot). A normal build without the define emits **no** benchmark lines. Keep one inspector, device, release/debug build type, network and GPS policy fixed. Prepare **ten distinct open assignments in staging**; tap Submit once per assignment. Use a separate 10-trial CSV for each evidence condition: none, preuploaded, or specified in-submit file size/count; don't use retries/duplicates as fresh submissions. Avoid mixing online taps with background offline syncing.

Capture only this app's logcat lines, ideally clearing device logs before a series. Each line starts `REVELA_BENCHMARK_CSV,` followed by **one CSV data row**. Put the header from `InspectionBenchmark.header` (`revela_mobile/lib/service/inspection_benchmark.dart`) first, and strip that prefix from each captured line; for example in PowerShell:

```powershell
adb logcat -c
# Perform ten manual staging submissions, then:
$header = 'scenario,trial,outcome,elapsed_ms,accepted_ms,visible_ms,request_id,http_status,registry_rows,map_rows,geolocated_rows,expected_markers,cache,network,evidence_files,preuploaded_urls,gps_fix,notes'
$lines = adb logcat -d -v raw | Select-String 'REVELA_BENCHMARK_CSV,' | ForEach-Object { ($_.Line -split 'REVELA_BENCHMARK_CSV,',2)[1] }
@($header) + @($lines) | Set-Content -Encoding utf8 inspection-responsiveness.csv
```

Check **exactly ten data rows**, including non-completed trials. Match `request_id` with backend request telemetry; it identifies the submit request, not the earlier evidence upload. Logcat can be lost if its buffer rotates: export promptly after each series. No report IDs, notes, images or credentials are logged.

## Isolated verification (no live APIs)

From `revela_web`: `node --test src/services/responsivenessBenchmark.test.js`; mocks dry-run success/failure, CSV export and marker/tile readiness gates without HTTP. From `revela_backend`: `.\.venv\Scripts\python.exe -B -m pytest -q tests/test_cors.py -k benchmark_request_id` tests the exposed request-ID header with an isolated Flask fixture. From `revela_mobile`: `flutter test --no-pub --dart-define=REVELA_BENCHMARK=true test/inspection_benchmark_test.dart test/offline_sync_reliability_test.dart` (and repeat the first test without the define to check opt-out); the fake Dio adapter never reaches a live server. These are tests, **not** ten real measurements; use the CSV process above only after staging approval.
